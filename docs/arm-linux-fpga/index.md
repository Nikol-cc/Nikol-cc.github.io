# RTOS 对比，核心差异

µC/OS-II、µC/OS-III 和 FreeRTOS 都是面向微控制器的实时操作系统内核，但它们在任务模型、优先级定义、资源管理、调试能力和生态支持方面存在明显差异。下面的对比以常见实现和默认配置为基础，具体行为仍应以目标版本、移植包和工程配置为准。

## 核心差异对比

| 维度 | µC/OS-II | µC/OS-III | FreeRTOS |
| --- | --- | --- | --- |
| 定位 | 较早、结构紧凑的经典实时内核，强调行为可预测和实现简洁 | µC/OS-II 的后续扩展，任务管理更灵活，诊断和运行时服务更丰富 | 面向广泛 MCU 平台的轻量内核，移植、示例和配套生态丰富 |
| 调度 | 固定优先级、抢占式；通常每个任务占用一个优先级 | 固定优先级、抢占式；同一优先级可有多个任务，并可轮转调度 | 固定优先级、抢占式；可按配置支持同优先级任务时间片轮转 |
| 任务数量 | 常见实现通常最多支持 64 个任务，其中部分优先级可能保留给内核 | 任务数量主要受 RAM、任务控制块和配置限制；支持同优先级多个任务 | 任务数量主要受 RAM、任务控制块、任务栈和配置限制 |
| 优先级 | 任务优先级通常同时承担任务标识作用；数值越小，优先级越高 | 任务标识与优先级分离；数值越小，优先级越高 | 数值越大，优先级越高；与 µC/OS 系列的方向相反 |
| 同步与通信 | 信号量、互斥量、消息邮箱/队列、事件标志等 | 包含 µC/OS-II 的主要服务，并支持更灵活的任务等待和调度 | 信号量、互斥量、队列、任务通知、事件组、软件定时器等 |
| 内存方式 | 任务栈通常由应用提供；内核对象和功能可通过配置裁剪 | 任务栈通常由应用提供；运行时服务和配置项更多，启用功能后 RAM 占用可能增加 | 动态创建较常见，也支持静态创建；可按配置裁剪内核和对象类型 |
| 调试与诊断 | 内核相对简洁，通常需要应用自行增加任务统计、栈检查和运行时诊断 | 内建的统计、运行时测量和任务管理服务更丰富，便于观察系统状态 | 基础内核较小，通常结合厂商调试器、运行时统计、Trace 工具和额外组件使用 |
| 移植与生态 | 历史移植较多，但需要确认当前芯片、编译器和 BSP 的质量与维护状态 | 同样需要确认具体移植包、组件版本和授权方式是否持续维护 | 芯片厂商、IDE、开发板示例、中间件和第三方工具支持广泛 |
| 许可 | 取决于实际使用的版本、发行渠道和授权条款 | 取决于实际使用的版本、发行渠道和授权条款 | FreeRTOS 内核当前采用 MIT 许可；其他配套组件需单独确认许可 |

## 需要特别注意的差异

### 1. 优先级数值方向不同

这是从 µC/OS 系列迁移到 FreeRTOS 时最容易出错的地方：

- µC/OS-II 和 µC/OS-III 通常是数值越小，优先级越高。
- FreeRTOS 通常是数值越大，优先级越高。

迁移任务表、互斥访问策略或中断唤醒逻辑时，不能只复制优先级数字。建议先建立一份“任务名称—原优先级—目标优先级—唤醒来源”的映射表，再逐个验证抢占关系。

### 2. 同优先级任务的支持方式不同

µC/OS-II 的经典模型通常要求一个任务对应一个优先级，因此任务设计往往会围绕唯一优先级展开。µC/OS-III 和 FreeRTOS 可以让多个任务共享同一优先级，但是否轮转、轮转周期多长，以及阻塞任务如何重新进入就绪队列，都可能受到配置项和移植层实现影响。

如果系统依赖严格的响应顺序，应使用明确的优先级和同步对象表达依赖关系，不要把时间片轮转当作任务间通信机制。

### 3. “实时”不等于“所有延迟都固定”

三种内核都可以实现抢占式实时调度，但最终响应时间还取决于：

- 中断关闭时间和临界区长度；
- 中断优先级、嵌套规则和 ISR 处理时长；
- 调度器实现、时钟节拍和时间片配置；
- 内存分配方式、缓存、总线竞争和外设 DMA；
- 任务本身是否存在优先级反转或长时间占用锁。

因此，选型时应在目标芯片上测量中断响应、任务切换、队列收发和最坏情况下的抖动，而不是只比较内核代码大小。

## 选型建议

| 场景 | 更适合优先评估的方向 | 主要原因 |
| --- | --- | --- |
| 既有 µC/OS-II 项目维护 | 继续使用 µC/OS-II，或评估 µC/OS-III | 可以减少迁移风险，保留现有任务模型和工程经验 |
| 需要更多任务、统计和运行时诊断 | µC/OS-III | 任务模型更灵活，内建运行时管理与诊断能力更丰富 |
| 新项目、MCU 型号较多、希望快速落地 | FreeRTOS | 移植包、芯片厂商支持、示例和社区资料通常更丰富 |
| RAM/Flash 非常紧张 | 对具体配置分别测量 | 内核大小只是起点，任务栈、队列、驱动和调试组件往往才是主要开销 |
| 有明确安全、商业授权或长期维护要求 | 先核对版本和授权，再做技术选型 | 不能仅根据内核名称判断许可、支持周期和认证能力 |

## 实际验证清单

1. 确认目标内核版本、移植层、编译器版本和芯片 BSP 是否匹配。
2. 统计每个任务的栈高水位、最大运行时间和最短唤醒周期。
3. 测量中断响应、任务切换、同步对象操作和队列满/空时的行为。
4. 检查互斥量是否支持优先级继承，并验证是否存在优先级反转。
5. 分别测试静态创建和动态创建的内存占用、失败处理与生命周期管理。
6. 使用 MAP 文件、`size`、运行时统计和 Trace 工具确认真实资源余量。
7. 将内核许可、商业组件、调试工具和长期维护成本纳入最终评估。

::: tip 结论

没有一种 RTOS 在所有项目中都更好。µC/OS-II 更适合维护经典、紧凑且模型稳定的项目；µC/OS-III 适合需要更灵活任务管理和更丰富诊断能力的系统；FreeRTOS 则通常更适合新 MCU 项目和重视生态、移植效率的团队。最终决定应以目标平台上的实测数据和工程约束为准。

:::
