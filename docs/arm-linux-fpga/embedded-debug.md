# 嵌入式调试与 DMA

## DMA 接收的基本流程

以 USART/RS422 DMA 接收为例，处理一帧数据通常不是简单地读取一个固定长度，而是根据 DMA 剩余传输数计算实际接收长度：

```c
len = (u16)(USART422_DMA_RX_SIZE
            - dma_transfer_number_get(DMA0, DMA_CH2));
```

一个可靠的乒乓缓冲流程通常包含以下步骤：

1. 暂停当前 DMA 通道；
2. 根据剩余传输数计算已经接收的数据长度；
3. 切换活动缓冲区；
4. 重新配置 DMA 的内存地址和传输数量；
5. 清理 DMA 标志并恢复通道；
6. 把已经完成的缓冲区交给上层协议处理。

这样可以让 DMA 接收和协议解析尽量解耦，减少在中断上下文中处理复杂协议的时间。

## 为什么会出现偶发丢包

排查 DMA 丢包时，不能只盯着串口波特率。还需要同时确认：

- DMA 通道是否在读取长度前被正确暂停；
- 切换缓冲区时，旧缓冲区是否仍被上层代码使用；
- DMA 标志是否及时清除；
- 缓冲区是否位于 DMA 可访问的 RAM 区域；
- 中断优先级和任务调度是否导致处理不及时；
- 缓冲区长度是否能覆盖最坏情况下的连续数据。

如果缓冲区放在片外 RAM，还要额外确认 DMA 控制器的地址访问能力、总线时序和缓存一致性问题。

## uCOS 任务栈

uCOS 中判断任务栈是否足够，不能只看任务当前是否运行正常。应通过系统提供的栈使用统计，观察高水位，并在任务增加日志、协议解析或临时数组后重新测量。

建议把以下信息一起记录：

- 任务优先级和周期；
- 栈总大小与历史最高使用量；
- 中断中是否调用了可能使用较多栈空间的函数；
- 协议缓存和 DMA 缓冲区是否错误地放在任务栈上。

## 定位硬件与软件边界

遇到“偶发错误”时，可以按这条路径缩小范围：

1. 先记录错误发生时的 DMA 计数器、缓冲区索引和状态寄存器；
2. 再确认中断是否实际到达，以及是否被重复触发；
3. 对照逻辑分析仪或示波器上的总线数据；
4. 最后检查任务切换、队列满、内存越界和缓存覆盖。

硬件问题和软件问题往往表现相似，只有把现场数据保留下来，才能避免靠猜测修改代码。
