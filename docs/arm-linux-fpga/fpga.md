# FPGA 工程方向

ARM Linux 和 FPGA 协同开发的核心，不只是“让 FPGA 跑起来”，而是建立一条可验证的数据通路：**硬件逻辑 → 总线接口 → Linux 驱动 → 用户态程序 → 上层功能**。

## 板级 bring-up 顺序

建议先把问题拆成几个可以独立验证的层次：

1. 电源、时钟、复位和下载配置是否正常；
2. ARM 侧是否能识别总线设备；
3. 设备树中的地址、中断和时钟描述是否与硬件一致；
4. 驱动能否读写 FPGA 寄存器；
5. DMA 或 FIFO 数据通道能否稳定传输；
6. 用户态程序是否能处理超时、错误和设备重启。

每一步都应该有一个最小可观察结果，例如寄存器读写回读值、中断计数、DMA 完成次数或错误码。

## 设备树与寄存器映射

设备树描述的是 Linux 对硬件资源的认识。地址范围、interrupt、clock、reset 和 DMA 配置有任何一个不一致，都可能表现为驱动探测失败、访问超时或数据偶发错误。

驱动调试时建议先完成最小寄存器访问，再逐步加入中断和 DMA。不要在寄存器地址还未确认时直接排查上层协议。

## DMA 数据通路

FPGA 数据量较大时，轮询寄存器通常不是最终方案。DMA 通道需要同时验证：

- 源地址和目标地址是否可访问；
- 数据宽度、突发长度和对齐方式是否一致；
- cache 是否需要 flush 或 invalidate；
- 中断是否能区分完成、半传输和错误状态；
- 环形缓冲或乒乓缓冲是否有明确的所有权交接。

这与 MCU 上的 DMA 调试原则相通：先确认数据是否真的到达，再判断协议解析是否正确。

## 记录规范

FPGA 联调时应保存版本号、bitstream、设备树、内核模块、测试命令和一段可复现日志。这样硬件逻辑变更后，才能判断问题来自 FPGA、Linux 驱动还是用户态程序。
